# Problem
    Everything I had done on the VM so far was manual. A real server needs to run repetitive tasks (backups, checks) without me being there.

# Objective 
    Write a simple Bash script and schedule it to run automatically with cron.

# What I did
    * Wrote *~/backup-test.sh*, a script that copies *~/test-perms* to a timestamped folder under *~/backup/* and logs the result.
    * Ran the script manually first to validate it before automating it.
    * Added it to my crontab with *crontab -e*, first at */5 * * * * to observe it quickly, using the script's absolute path.
    * Checked *~/backup.log* to confirm the automatic runs.

# What worked vs what got stuck

    ## What worked
        * The script ran correctly by hand.
        * The cron job executed on schedule and appended entries to the log.

    ## What got stuck
        * Cron reported *backup: command not found*, even though I never called a command named *backup*. The real cause was an *invisible character* in the script (likely introduced by copy-pasting between my host and the VM), which made Bash misread a line and try to run part of it as a command.
        * My first version of the success/failure check had several syntax errors at once:
            * *If* written with a capital letter - Bash is case-sensitive, so *If* is not the same command as *if*.
            * [$? -eq 0 ] - missing space right after [. The [ is itself a program (a command), and like any command it needs its arguments separated by spaces, so [$? was read as a single, invalid argument.
            * "($date '+%F %T' - Copie reussie)" - I was not capturing the output of *date*. The correct syntax is command substitution, $(date '+%F %T'), not just prefixing the variable-like text with $. There was also a stay closing parenthesis with no matching opening one.
        * I fixed each issue one at a time and verified with *bash -n backup-test.sh*, which checks the script's syntax without running it.

# My reasoning
    * I used absolute paths everywhere in the script and in the crontab line, because cron does not run with my interactive shell's environment: its starting directory and *PATH* are different, so a relative path would not resolve to the same location as when I run the script by hand.
    * I tested at */5 * * * * first instead of the final schedule, to see several log entries quickly and confirm the automation worked before committing to a realistic frequency.
    * I checked *bash -n* after every single fix instead of changing everything at once, so I could be sure which correction solved which error.
  
# Open questions
    * Beyond copy-pasting between host and VM, what other situations commonly introduce invisible characters into a script, and how can I catch them earlier next time?
    * What is the cleanest way to confirm cron actually attempted to run the job, beyond reading my own log (for example through the system logs)?

# Final solution
    A working, syntactically valid Bash script that backs up a folder with a timestamp, logs success or failure using the exit code of the copy command, and runs automatically every 5 minutes via cron using absolute paths.
