# Problem
    Level 1 only ever involved a single isolated VM. NetLabOps is supposed to simulate a company network, but there was no actual network yet - nothing to connect, nothing to resolve addresses between.

# Objective
    Build the smallest possible network in eNSP (two PCs connected through one switch), and understand how two devices on the same subnet actually find each other at the Ethernet level, before any routing is involved.

# What I did
    * Build a topology in eNSP with 2 PCs and 1 switch, connected with Ethernet links.
    * Assigned static IPs in the same subnet: 192.168.1.1/24 for PC1 and 192.168.1.2/24 for PC2.
    * Displayed PC1's ARP table before pinging PC2.
    * Pinged PC2 from PC1, then displayed the ARP table again.
    * Waited a few minutes without generating traffic, then checked the ARP table a third time.
    * Changed PC2's IP to a different subnet (192.168.2.2/24) without adding a router, then pinged again from PC1 to observe the failure.

# What worked vs what got stuck

## What worked
    * Same-subnet ping succeeded once both PCs had IPs in 192.168.1.0/24.
    * ARP table was empty before any traffic, then populated with MAC address, IP address, and type(dynamic) after the ping.
    * After a few idle minutes, the ARP table emptied out again on its own.
  
## What got stuck (and what I corrected)
    * My first explanation for entry explanation only covered configuration changes (a device could get a new MAC while keeping the same IP). I was missing the other main reason: memory and relevance - a device only keeps entries for what is actively in sue, so expiration keeps the table reflecting the current state of the network rather than accumulating stale records forever.
    * When I switched PC2 to a different subnet (192.168.2.2/24). I first reasoned that the failure was because "ARP operates at Layer 2 but packet transmission needs the IP protocol at Layer 3". That reasoning was wrong: ARP is not blocked by needing an IP - resolving an IP to a MAC is exactly ARP's job. The real issue is a prior decision PC1 makes before even trying ARP: whether the destination IP is on the same local network at all.
    * I initially thought this decision was made by directly comparing subnet addresses. The actual mechanism is a subnet mask calculation: PC1 applies its own mask to its own IP and to the destination IP (bitwise AND) to get each one's network portion. If the two network portions match, the destination is "on-link" and ARP is used directly. If they don't match, PC1 concludes the destination is remote and looks for a configured default gateway instead of attempting ARP at all.
    * The cross-subnet ping returned Destination Host Unreachable. This error comes from PC1 itself, locally, before any packet even leaves the machine: since no default gateway was configured, PC1 had nowhere to forward a packet meant for a different subnet.

# My reasoning 
    I predicted each result before testing it (same-subnet ping should work, cross-subnet should fail) instead of just running commands and observing. When my first explanation for the cross-subnet failure turned out to be imprecise, I reasoned through the actual decision process a device makes (mask comparison, not address comparison) before re-testing, which matched the observed error.

# Open questions
    * If I later configure a default gateway address on PC1 without adding an actual router device in the topology, I expect the ping to still fail, because a gateway address is only a meaningful if a real device is listening at that address to forward the packet onward. I want to verify this directly in N2.2 once a router is introduced.

# Final solution
    Two PCs on the same subnet (192.168.1.0/24), connected through a switch, successfully pinging each other, with a populated and readable ARP table (MAC address, IP address, dynamic/static type). Confirmed that cross-subnet communication fails without a router, and that the failure originates from the sending host's own subnet-mask comparison, not from the switch or the destination.

# Commands used(eNSP PC terminal)
    arp -a                  # show the ARP table
    ping 192.168.1.2        # same-subnet ping (success)
    ping 192.168.2.2        # cross-subnet ping without a gateway (failure)
