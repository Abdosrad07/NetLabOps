
 **Tool:** Cisco Packet Tracer | **Status:**  Solved (4/4 scenarios)

## 1. Problem

Four faults were injected one after another into the NetLabOps topology (router-on-a-stick, VLANs, OSPF, NAT/PAT). For each one, the goal was to find the root cause with a method (hypothesis → test → observation → conclusion → fix) instead of guessing.

## 2. What I did not know / needed to understand

- How to isolate a fault layer by layer (L1/L2 → L3 → services/NAT).
- Which `show` commands give proof, not just a feeling.
- How a client's own subnet-mask calculation decides whether it even attempts ARP, versus how a switch can silently drop a broadcast regardless of IP addressing.
- How NAT behaves when interfaces are subinterfaces (router-on-a-stick).

## 4. Scenario A – interface administratively down

**Hypothesis (before testing):** shutting down R1's VLAN 20 subinterface would make its gateway unreachable, so PC3 would fail to reach anything beyond its own subnet. Predicted the first visible symptom would be PC3 unable to reach its own gateway (`192.168.20.254`) — testing that single hop before attempting the full PC3 → PC1 path, the same way the gateway hop was isolated in N2.2.

**Test:**

```
interface FastEthernet0/0.20
 shutdown
```

Then: `ping 192.168.20.254` from PC3.

**Observation:** `Request timed out` on the gateway ping, confirming the hypothesis. Rather than assuming the cause from memory of what had just been typed, the state was verified with a command:

```
show ip interface brief
```

Output showed `FastEthernet0/0.20 ... administratively down ... down` — direct proof of an operator-caused shutdown, not a cable or addressing fault.

**Conclusion:** a subinterface disabled with `shutdown` takes down everything routed through it, even though the physical parent interface and the other subinterface (VLAN 10) remain completely unaffected.

**Fix:**

```
interface FastEthernet0/0.20
 no shutdown
```

**Verification:** re-tested in two steps — PC3 → Router1 (gateway) succeeded, then PC3 → PC1 succeeded, confirming the fix restored the full path, not just the first hop.

## 5. Scenario B – asymmetric subnet masks

**Hypothesis (before testing):** changing PC2's mask from `/24` to `/25` (while leaving its IP and PC1's IP/mask untouched) would put PC1 and PC2 into different subnets, breaking connectivity in at least one direction.

**Verification by calculation (before touching the lab):**

- PC1: `192.168.10.1`, mask `/24` → network `192.168.10.0/24`.
- PC2 (new): `192.168.10.2`, mask `/25` → network `192.168.10.0/25`.
- Both addresses fall in the **lower half** of the `/24` range (`.0`–`.127`), so PC1's own `/24` calculation and PC2's own `/25` calculation agree: both still consider each other on-link. **No asymmetry occurs with this specific addressing** — the initial hypothesis of a break was wrong for this particular IP choice.

**Correction of the hypothesis:** an asymmetry would only appear if one host's address fell in the **upper half** of the `/24` range (`.128`–`.255`), where a `/25` calculation yields a different network than the `/24` calculation. Example worked out: if PC2 were `192.168.10.240/25` instead, its own network would compute to `192.168.10.128/25`, while PC1 (`192.168.10.1`) would remain in `192.168.10.0/25` from PC2's point of view — producing a one-directional failure (PC1 → PC2 still works, since PC1's `/24` sees PC2 as on-link; PC2 → PC1 fails, since PC2's `/25` does not).

**Conclusion:** mask mismatches do not always break connectivity — the result depends entirely on where each address falls within the range implied by the *narrower* mask. This is a subtle, easy-to-miss fault in real networks because testing a ping in only one direction can hide the problem.

**Fix (for the addressing actually used):** none required — the chosen test addresses did not produce a fault. The exercise's value was in proving, by calculation, why a mask change does *not* always cause the symptom intuition suggests, and identifying precisely which addressing would.

## 6. Scenario C – wrong VLAN membership

**Hypothesis (before testing):** moving PC4's switch port from VLAN 20 to VLAN 10 — without touching PC4's IP, mask, or configured gateway — would not trigger an immediate local error like the gateway-less case in N2.1 (PC4's own mask calculation still considers `192.168.20.254` on-link, since nothing in PC4's own configuration changed). Instead, PC4 would genuinely attempt an ARP broadcast for its gateway, which the switch would then fail to deliver correctly, since the port no longer belongs to VLAN 20. Predicted several timeouts rather than one immediate rejection — the same pattern observed with VLAN isolation in N2.3.

**Test:**

```
interface <PC4's port>
 switchport access vlan 10
```

Then, from PC4: `ping 192.168.20.254`, followed by `arp -a`.

**Observation:**

```
Pinging 192.168.20.254 with 32 bytes of data:
Request timed out.
Request timed out.
Request timed out.
Request timed out.

Ping statistics for 192.168.20.254:
    Packets: Sent = 4, Received = 0, Lost = 4 (100% loss),

C:\>arp -a
No ARP Entries Found
```

Four full timeouts, not an immediate local rejection, and a completely empty ARP table — confirming the ARP broadcast was sent but never answered, exactly as predicted.

**Conclusion:** VLAN membership is enforced by the switch independently of any IP/subnet configuration on the host. A host can have a perfectly valid gateway address and still be unable to reach it if its physical/logical port placement contradicts its intended VLAN — the same category of fault demonstrated conceptually in N2.3, here caused by an operator mistake rather than deliberate same-subnet testing.

**Fix:**

```
interface <PC4's port>
 switchport access vlan 20
```

**Verification:** re-tested `ping 192.168.20.254` from PC4 — 100% success, restored.

## 7. Scenario D – NAT misconfigured

**Hypothesis 1:** the packet leaves with its private source IP, so the external host has no route back to it.

**Test:** ping from PC1 to the external host, then on the border router:

```
show ip nat translations
show ip nat statistics
```

**Observation (before fix):**

- `Total translations: 0`
- `Hits: 0 / Misses: 11`
- `Dynamic mappings:` empty → no translation rule active.

**Conclusion:** a PAT needs three elements: an inside interface, an outside interface, and a translation rule. Interfaces were checked first, then the rule was found missing. Moreover, PC1 sits in a VLAN, so its traffic enters through the **subinterface** (`Fa0/0.10`), not the physical interface.

**Fix:**

```
access-list 1 permit 192.168.10.0 0.0.0.255

interface FastEthernet0/0.10
 ip nat inside

interface FastEthernet1/0
 ip nat outside

ip nat inside source list 1 interface FastEthernet1/0 overload
```

**Verification (after fix):** `show ip nat translations` now shows ICMP entries translating the inside local address `192.168.10.1` to the inside global `203.0.113.1`, toward `203.0.113.2`, with a distinct ID per echo. `Total translations: 4 (4 extended)`, `Hits` increased, and the inside interfaces list includes `FastEthernet0/0.10`.

## 8. Lessons learned

1. In a router-on-a-stick design, `ip nat inside` goes on the **subinterface** carrying the VLAN traffic, not the physical parent interface.
2. An empty NAT table during a ping means no translation happens; check interfaces **and** the rule.
3. Pinging from the router itself does not test NAT (that traffic does not traverse it). Always test from the client.
4. `show ip nat statistics` (interfaces, hits/misses, rule) is the fastest NAT health check.
5. A disabled subinterface (`shutdown`) only affects what is routed through it — siblings on the same physical interface stay unaffected.
6. A mask mismatch does not automatically break connectivity; the actual effect depends on where each address falls relative to the narrower mask's range — always verify by calculation, not intuition, and test both directions.
7. Wrong VLAN membership produces silent ARP failures (full timeouts, empty ARP table), not immediate local errors — because the host's own configuration looks entirely valid; only the switch's enforcement is at fault.
8. Prove each hypothesis with a command output before changing the config.

## 9. Troubleshooting method (reusable checklist)

1. Define the exact symptom (who, to where, what works).
2. L1/L2: interface state, VLAN membership.
3. L3: IP/mask, gateway, routing table.
4. Services: DHCP/DNS/NAT, using their dedicated `show` commands.
5. Change one thing, retest, document.
